## 1. Цель и ПОСЛЕДНЕЕ требование пользователя

Нужно **глубоко классифицировать все 2584 активных Product категории «Макияж»** (`ru`) для multi-value relation `product_features` с **ровно тремя финальными состояниями на уровне Product**:

1. `assigned` — одно или несколько значений `product_features` убедительно подтверждены; сохранить список кодов и источники.
2. `not_applicable` — ни одно значение справочника **объективно не может относиться к назначению этого типа товара**; необходимы понятное основание и проверяемая категорийная/продуктовая семантика.
3. `review` — потенциально применимо, но не удаётся надёжно подтвердить ни одно значение; сохранить причины неопределённости и приоритет проверки.

**Состояния `[]`, `no_claim`, `no_confirmed_claim`, `unknown` как ФИНАЛЬНЫЕ запрещены.** Отсутствие явного заявления не доказывает неприменимость: если нет оснований для assigned/not_applicable, ставить `review`. Нельзя просто переименовать все старые `[]` в `not_applicable`, нельзя выдумывать свойства ради 90%. Дополнительные сомнения по отдельным признакам у уже assigned Product хранить как `review_codes` / `partial_review`, **не блокируя** присвоение подтверждённых значений. Итоговый product-level status для такого Product — `assigned`. После полного аудита строго проверить `assigned + not_applicable + review = 2584`; 0 иных/пустых статусов.

**Общая цель полноты:** уверенно классифицировать не менее ~90% действительно применимых товаров при доказуемом denominator, но точность выше KPI. Окончательный denominator нельзя определять как только товары с уже найденными свидетельствами; в него должны попадать и review, когда свойства могут быть применимы. Если до цели не дойти без догадок — показать честную долю и оставить review, не подменять классификацию.

**Критичное решение по охвату:** значения фильтра **не привязаны исключительно к туши**. `volumizing` может описывать средство для губ/бровей/ресниц, если заявлен реальный косметический эффект объёма. `waterproof` применим также к подводке/карандашу/тону, `hypoallergenic` — к разной косметике. Категория — подсказка семантики, не жёсткий запрет.

## 3. Семантика — обязательные защитные правила

- `waterproof`: прямые **waterproof / water-resistant / водостойкий / устойчивость к воде, поту, слезам**, если достаточно конкретна. Просто `long-lasting`, `smudgeproof`, `transferproof`, «стойкий» **не достаточно**.
- `curling`: явно подкручивает/приподнимает ресницы; изогнутая кисть сама по себе не доказательство.
- `lengthening`: явно удлиняет ресницы или другой релевантный эффект удлинения по утверждению изготовителя; не выводить из формы щёточки.
- `contact_lens_wearers`: изготовитель прямо подтверждает совместимость с ношением контактных линз. «Для чувствительных глаз» или «офтальмологически протестировано» сами по себе **не достаточны**.
- `volumizing`: прямо заявленный эффект объёма/пышности/уплотнения, относящийся к внешнему эффекту продукта; **не** объём упаковки и не размер щёточки. Применимо также к пламперам/блескам для губ, средствам для бровей.
- `hypoallergenic`: строго явный `hypoallergenic / гипоаллергенный` или подтверждённый эквивалент производителя. «Sensitive», «dermatologically tested», «ophthalmologically tested», `Allergy Certified` без равнозначного заявления **не присваивать автоматически**.
- Разрешены несколько кодов на один Product. `review` одного не блокирует `assigned` других. **Не брать `attributes` (торговые предложения) за источник смысла product_features**; использовать Product + бренд/категории/форму + при необходимости официальные источники.

## 7. Content Manager API: подтверждённые подходы, но live source выше

Strapi Admin: `http://10.10.3.80:1337/admin`; auth session `localStorage.jwtToken` **только в DevTools пользователя**, не в документацию/логи/файлы. Product UID `api::product.product`, locale `ru`, ключ `documentId`.

Примеры существовавших запросов (перед записью проверить фактический Network):

```text
GET /content-manager/collection-types/api::product.product/<documentId>?locale=ru
GET /content-manager/relations/api::product.product/<documentId>/product_features?locale=ru&pageSize=100&page=1
GET /content-manager/relations/api::product.product/<documentId>/categories?locale=ru&pageSize=100&page=1
```

По прежнему workflow частичное обновление relation имеет форму:

```text
PUT /content-manager/collection-types/api::product.product/<documentId>?locale=ru
{"product_features":{"connect":[{"id":<LIVE_NUMERIC_CM_ID>,"documentId":"<TARGET_DOC_ID>","locale":"ru","isTemporary":true}],"disconnect":[]}}
```

Публикация:

```text
POST /content-manager/collection-types/api::product.product/<documentId>/actions/publish?locale=ru
{}
```

Правила: before write сверять текущие draft/modified/relations; не трогать modified/draft; сохранять existing; сравнивать по `documentId`; `disconnect` нельзя; `PUT`/publish `POST` автоматически НЕ retry; читать все страницы; пилот + верификация; низкая concurrency, pause/checkpoint, итоговый CSV; идемпотентный rerun.

Официальный `project/context.md` содержит CANONICAL `product filter enrichment workflow`, но старый `assigned / [] / review` для этой конкретной задачи **заменён** новым 3-state правилом `assigned / not_applicable / review` с запретом `[]`.
