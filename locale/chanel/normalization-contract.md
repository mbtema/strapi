# CHANEL — контракт нормализации категорий RU → KK

> Статус: согласованные правила и результаты **read-only** проверки от 18.11.2026. Это не разрешение на массовые записи. Реальная реализация PUT/POST для CHANEL ещё не проверена.

## Scope и источник

- Только бренд CHANEL: `api::brand.brand / yeag7mng9hfpk7pd4ggm7495`, RU relation `categories`; первичный список `chanel-categories-ru.json` содержит 65 уникальных Category `documentId`.
- RU **Draft** — источник семантических значений; реальный список записей и данные перечитывать непосредственно перед каждым изменением, не считать экспорт актуальным live state.
- Для каждой Category учитывать RU/KK Draft и Published, включая **все** root relations и доступные nested relations. Снимок RU/KK до изменения, postflight проверка после каждого PUT/POST, экспорт файлов. Статус `modified` сам по себе не означает несогласованное изменение.
- Создание KK, обновление полей и публикация — отдельный write-этап, после защитного пилота. Снимок в JSON/IndexedDB не заменяет независимую резервную копию БД при риске повреждения Strapi i18n. Для пилота первой Category пользователь прямо подтвердил отсутствие DB backup и согласился отложить **нормализацию** `key`. Это не отменяет контроля его целостности.

## Обязательная публикация обеих локалей — решение пользователя 18.11.2026

**Критерий успешной нормализации — контентная однородность между RU и KK на стороне клиента, а не только совпадение Draft.** Пользователь явно подтвердил обязательную публикацию **и RU, и KK** для каждой Category. Оставлять актуальные изменения в статусе `draft`/`modified` вместо Published нельзя.

- После нормализации добиться опубликованной RU версии, соответствующей исходному **актуальному RU Draft**, и опубликованной KK версии, соответствующей нормализованному KK Draft. В частности, согласовано публикацией RU вывести новые `dynamic`-баннеры, `showProducts=true` и изменённые `filters_app` там, где они отличаются от прежней RU Published.
- Если RU уже Published и по всем бизнес-полям/relations семантически идентична актуальному RU Draft — повторный RU Publish без необходимости не делать; если есть отличия либо RU Published отсутствует — RU Publish обязателен. То же правило проверки применимо к KK Published.
- Перед **каждым** PUT/POST/Publish снять и сохранить четыре текущие версии и root/nested relations. После KK write RU Draft и RU Published не должны изменяться; после RU Publish допустимо **только запланированное обновление RU Published до актуального RU Draft**. RU Draft остаётся неизменным; остальные локали/поля/медиа/relations проверяются на непредусмотренные изменения. После KK Publish допускается только ожидаемое обновление KK Published до нормализованного KK Draft. Системные идентификаторы версий, timestamps и numeric component instance IDs не являются бизнес-изменениями.
- На этапе postflight проверять **обе Published версии**: актуальные значения, связи по `documentId`, сохранность локализованных KK-медиа/переводов и корректность RU. Если published nested relation API позволяет проверить только count, это ограничение сохранять в отчёте; нельзя утверждать, что точный опубликованный состав доказан.
- Обе публикации — последовательные операции, не атомарная транзакция. Если одна запись/публикация не завершилась или postflight не доказал корректность, Category помечается `partial/pending` или запуск останавливается при нарушении целостности; **не считать такую Category полностью нормализованной**.
- Известные проблемы Strapi i18n с shared `key` не отменяют обязательную RU Publish: прежде нужен безопасный пилот на конкретной Category. При потере ключей/любой RU drift немедленно GLOBAL STOP, сохранить snapshots, без автоматического восстановления/повторной записи. В общем массовом write-процессе резервная копия БД настоятельно рекомендуется. **Исключение:** первый publish-only пилот разрешён пользователем без независимого backup при отдельном одноразовом подтверждении риска в Console, до POST — обязательные browser snapshots и проверка сохранности `key`. При фактическом повреждении JSON/IndexedDB не обеспечивают автоматическое восстановление БД.

## Уточнённое пользователем правило Media — 18.11.2026

**Любое уже заполненное Media в KK сохранять**, даже если его numeric ID или сам файл отличается от RU. Это действует на все Media schema-типа — корневые, внутри обычных и повторяемых компонентов и на любой глубине Dynamic Zone, включая `dynamic[].items[].image`, `brandZoneBanners[].image` и другие вложенные поля. Не зависеть от `pluginOptions.i18n.localized`: содержимое KK защищено независимо от флага, пока реальные postflight-проверки не подтвердят отсутствие кросс-локальных побочных эффектов.

- При ненулевом Media в KK сохранить **точный KK asset**; сравнивать по ID/составу, но не переносить русское Media в KK просто из-за отличия объектов.
- Если соответствующее Media в KK пусто — копировать существующее RU Media. Если и RU пусто — без изменения.
- При **новой** KK-локали, где своих Media нет, первоначально используются RU Media в доступных компонентах, если позволяет схема и подтверждённый save contract.
- Различия numeric `id` самих экземпляров компонентов RU/KK не являются бизнес-расхождениями и не повод пересоздавать компоненты.
- Повторяемые компоненты сопоставлять по устойчивым полям (`key`, `__component` и др., если реально уникальны), а не по индексу или numeric ID. При неоднозначности соответствия **пропуск/ручной review**, а не замена всего KK блока.
- Оставшиеся согласованные семантические поля и связи компонента синхронизировать RU → KK, но без уничтожения защищённых KK Media. В том числе нельзя слепо отправлять целиком RU `dynamic` поверх KK.

## Прочие правила нормализации

- `name`: сохранить существующий непустой KK перевод; если KK пусто — заполнить из RU. `title`, Boolean (`active`, `custom`, `showProducts`) и остальные ранее согласованные не-медиа поля нормализовать от RU, с проверкой настоящей schema и ограничений уникальности.
- `productsLabelFilter`, `brandZoneBanners`, `filters_app`, `dynamic`: зеркалировать согласованные значения и порядок с глубокой защитой Media; nested relations проверять по реальным `documentId`, отдельно разрешая KK targets.
- Root relations `parent`, `categories`, `product`, `brand`, `top_brands`: RU состав → соответствующие KK targets; отсутствующий KK target записывать как pending link и продолжать независимые поля. Не создавать и не менять чужие Product/Brand автоматически. Перед созданием parent/children links может потребоваться сначала создать все 64 отсутствующие KK Category.
- Устаревшая `products` должна быть пустой RU/KK; непустая RU — явный stop/review для записи, лишние KK links удаляются только по согласованному правилу.
- `key` — **nonlocalized unique shared**: известен live-инцидент с обнулением RU Draft.key при KK PUT. **По решению пользователя 18.11.2026 нормализацию `key` полностью отложить** для отдельного механизма. Не генерировать, не выравнивать, не PUT `key` в KK. При стандартной публикации Strapi сохранять исходный `Draft.key` в полном Publish payload по текущему подтверждённому CM контракту и обязательно проверять значения RU/KK в postflight; отличия регистрировать в review. Уникальный `bitrix_id` также требует предварительной проверки, не угадывать допустимость дублей при создании KK.
- Перед каждым write сохранять полные snapshots четырёх версий/relations, затем проверять семантику RU Draft/Published неизменной. При RU drift, неопределённом ответе PUT/POST, повреждении ключа — GLOBAL STOP, сохранить before/after; никакого автоматического повторного PUT/POST или слепого восстановления.

## Результаты read-only аудита (18.11.2026)

Файл пользователя: `chanel-categories-audit-all.json` (в репозиторий **не загружается**; содержит полные бизнес-данные CMS). Запуск `locale/chanel/categories-audit-all.js` с `complete=true`: 65/65 записей, 1 044 GET, retries=0, errors=0.

- RU Draft: **65/65**, RU Published: **64/65**.
- KK Draft: **1/65** (только `adl0ggt49f808cv4j2xalioq` / `Chanel / Holiday Collection`), KK Published: **0/65**.
- У существующей KK `dynamic[0].items[0].image.id=153056` (KZ-изображение) отличается от RU `153055` (RU-изображение). **Сохранить 153056**. Семантические root relations этого Category совпадают: `product` 10/10 и `brand` 1/1.
- Во всех 65 RU Draft есть 1 `brand-page.banner-slider`. Во всех **64** существующих RU Published `dynamic=[]` и `showProducts=null`, тогда как RU Draft `dynamic` содержит баннер и `showProducts=true`; у **4** дополнительно отличается `filters_app` (Draft заполнено, Published пусто). Поэтому **RU Publish изменит публичный RU-контент**. Пользователь **18.11.2026 подтвердил**, что эти изменения **необходимо публиковать**, как и соответствующий KK-контент. Прежний общий Category Localizer по умолчанию не публикует RU из-за известных i18n-рисков; CHANEL требует отдельного проверенного write-пути и строгого postflight.
- Root relation в RU Draft: `product` суммарно 978 связей (321 уникальный Product `documentId`), `brand` 65, `parent` 60, `categories` 60; `products` и `top_brands` пусты. Десять parent Category и все 60 child targets входят в текущие 65; наличие KK у 321 Product **не проверялось**.
- RU `key` заполнен и уникален у всех 65; значения KK `key` остальных 64 пока отсутствуют вместе с локалями. Все 65 RU `title` заполнены. Схема root Media: `largeImage_app`, `preview_picture`, `previewImage_app`, `largeImage`, `detail_picture`, `menu_banner`, `pictures`.

### Реализованный первый пилот (код, ещё не live-tested)

- `locale/chanel/category-first-publish-pilot.js` — **строго первая** `Chanel / Holiday Collection` (`adl0ggt49f808cv4j2xalioq`), уже имеющая RU/KK Draft со совпадающими бизнес-полями/relations и различающимся, но защищённым KK-изображением. Скрипт использует проверенные GET и Content Manager Publish API из Category Localizer; `PUT`/создания KK нет.
- По умолчанию выполняет **только GET** и скачивает dry-run JSON с `baselineHash` и точным планом. В write-режим переходит только через три одноразовых флага (apply token, явное согласие с отсутствием DB backup, SHA-256 dry-run); до каждого POST сохраняет снимки в browser IndexedDB и скачивает JSON, сверяет свежую бизнес-семантику всех 4 версий с checkpoint, затем последовательно отправляет максимум 2 `POST` Publish: RU и KK. При невозможности записать browser journal — запрет дальнейшего POST.
- Payload для Publish, как в действующем Category Localizer, включает текущее неизменённое `Draft.key` (это **не** нормализация и не PUT `key`). При этом известен live-risk cross-locale key incident: независимая копия БД и postflight 4 версий обязательны; успешный кодовый dry-run не гарантирует безопасный Publish Strapi.
- Snapshot/ожидаемый Published сравниваются по schema-полям (media по ID, компоненты без numeric instance ID), root relations по полному составу `documentId`; все нецелевые версии после каждого Publish должны остаться неизменны. Нет автоматического повтора неясного POST. Вложенные связи с ненулевым count требуют отдельного проверенного контракта и блокируют данный пилот.
- Пилот намеренно **не исправляет несовпадения KK Draft**: если какая-либо структура, relation или нужное не-медиа поле различаются, блокирует публикацию. Это проверка безопасной публикации и сохранности переводных медиа, **не** готовый массовый нормализатор. Следующий этап — пилот создания KK для одной из 64 отсутствующих локалей, после проверки полного publish-only пилота.

**Подтверждено по всем 7 пользовательским JSON снимкам**, включая `before`, `pending-ru`, `after-ru`, `pending-kk`, `after-kk`, `apply` и `dry-run`.

- Итог `category-first-publish-pilot.js`: `status=integrity-stop`, `108 GET`, `2 POST`, `0 PUT`, `0 retries`, ошибка `Published kk не совпал с Draft после Publish`. Оба POST получили штатный HTTP-ответ (`postError=null`), ошибка выявлена при **последующей GET-сверке**.
- RU Published создан `id=12618`, `publishedAt=2026-11-18T09:18:13.902Z`; RU Published семантически соответствует RU Draft, включая **10 links `product`** и исходное русское изображение `153055`.
- KK Published создан `id=12619`, `publishedAt=2026-11-18T09:18:16.705Z`, сохранил **KK media `153056`**, `key=cf7f4a203aed93a8`, `brand` и другие schema-fields; **одна доказанная бизнес-разница** между KK Draft и KK Published — `relations.product` содержит **0 вместо 10** `documentId`. `raw.product.count=0` у KK Published (это не только сбой сравнения). KK Draft по-прежнему содержит все 10 ссылок.
- Точная независимая Python-сверка схемно значимых `fields` (Media по ID, Component instance ID игнорировать) и всех root relations `documentId` показывает 0 отличий между RU Draft и RU Published; 0 непредусмотренных изменений RU Draft, RU Published и KK Draft до/после второй публикации (кроме меняющихся внутренних component numeric IDs и timestamps). Единственное нарушение — отсутствие 10 links в KK Published.

Никакого автоматического retry или вручную запуска того же Publish**, и никакого перехода к остальным 64 Category; Category находится в partial state, пока KK Published не восстановит 10 корректных связей. Это наблюдаемое следствие Strapi Publish для данной категории, но механизм пока не доказан: возможно связь хранится на обратной стороне Product и зависит от KK Published Product, нельзя утверждать без проверки.
- Создан read-only скрипт `locale/chanel/published-product-links-audit.js`: проверяет 4 Category версии и обратные связи `Product.categories` для 10 Product в RU/KK Draft/Published, автоматически выгружает `chanel-published-product-links-audit.json`. Не выполняет ни одной записи. Дальнейший repair/write contract обсуждать только после проверки его результата.

### Безопасный порядок дальнейшей работы

1. **Решено:** обязательно публиковать обе локали, RU Published должна отражать текущий RU Draft (включая 64 новые публикации баннеров), KK Published — нормализованную KK версию.
2. Разработать read-only точный план создания 64 KK, зависимостей, ограничений уникальности, глубокого merge Media и обеих публикаций; готовность считать по Published, не Draft.
3. **Пилот выполнен и завершился `integrity-stop`.** Не повторять публикацию: KK Published потерял 10/10 root `product` links. Сначала пройти `published-product-links-audit.js` (только GET), установить механизм и отдельный безопасный repair. Никакого создания 64 KK/массового запуска до полноценного postflight Published RU+KK.

### Решение по резервной копии и `key` — 18.11.2026

Пользователь сообщил, что копии БД нет, а нормализацию `key` выполнит позже отдельным механизмом. **Не требовать ложного подтверждения DB backup** для уже согласованного узкого publish-only пилота одной Category. Вместо этого требуется отдельный флаг `tmChanelPilotNoDbBackupRiskAcceptedOnce` и SHA-256 из проверенного dry-run. Перед POST обязательно сохранение текущих snapshots на клиенте в IndexedDB (`tm-chanel-pilot-journal-v1`) и попытка JSON скачивания; останавливать выполнение при сбое browser journal. При повреждении `key` или других данных — глобальный стоп без автоматического исправления. Пользователь должен понимать, что JSON/IndexedDB не замещают восстановление из серверного DB backup. `key` не нормализуется, но контролируется после каждой публикации.
