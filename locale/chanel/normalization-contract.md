## Операционный порядок

1. Из живого Content Manager `Brand.categories` (`locale=ru,status=draft`, все страницы) получить ровно 65 уникальных `documentId`; сверить schema Category и компонентов. Script запускается на RU Brand CHANEL. **Любой запуск скрипта сразу production** — dry-run и обязательных флагов больше нет. Скрипт сначала читает состояние, затем выполняет только действительно необходимые PUT/POST; повторный запуск на актуальной CMS обычно заканчивается без записей. Состояние `modified` означает, что Published может требовать обновления, а не чужое изменение или причину блокировать Save. Устаревшие `tmChanelProductionOnce` и `tmChanelNoDbBackupRiskAcceptedOnce` игнорируются и очищаются.
2. **Content:** для каждой Category взять текущий RU Draft и KK Draft. Если KK нет — создать одной `PUT /content-manager/collection-types/api::category.category/{documentId}?locale=kk` с полями RU (Media по ID, Dynamic Zone и все вложенные компоненты по схеме). Если KK есть — обновить только расхождения; сохранить существующие локализованные KK тексты и Media на любой глубине, в частности KK Holiday Collection image `153056` вместо RU `153055`. Фильтры `filters_app` брать из RU. `name` и прочие локализованные тексты существующего KK сохранять. Никогда не нормализовать root `key`/ `code`/`slug`, но проверять их неизменность и корректность после создания. Unique `bitrix_id` с положительным RU контролем.
3. **Relations:** после создания всех доступных KK Category добавить только отсутствующие root `parent`, `brand`, `product`, сопоставив целевые KK Draft по `documentId` и взяв их актуальные numeric `id`. Использовать `{connect:[{id,documentId,locale:'kk'}],disconnect:[]}`. Один PUT/пачка, максимум 20 добавляемых links. **Никаких disconnect, изменения чужих записей, рекурсивной публикации Product или автоматической записи inverse-полей `categories`/`products`/`top_brands`.** Обратная `categories` проверяется как следствие заполнения `child.parent`, `product` — прямая связь Category к KK Product Draft. Если KK target отсутствует, Category помечается incomplete; не считать её нормализованной.
4. **Publish:** только при полном соответствии RU/KK Draft по плановым полям и root relation `documentId` выполнять последовательные `POST .../actions/publish?locale=ru`, затем `kk`. Не публиковать Product/Brand или другие targets. Пропускать уже актуальные опубликованные версии. После каждого POST проверять неизменность RU/KK Draft, наличие нового Published, совпадение полей/Media/`key` с Draft и отсутствие посторонних Published links. Published может содержать **меньше** links, чем Draft, если target ещё не опубликован — это информативное отличие, не ошибка. Статус двух локалей и скрытые Published links включать в итоговый отчёт.
5. **Защита:** Content Manager GET по четырём версиям, native relations по всем страницам, сверка источника и получателя после **каждой** записи. Перед записью запись pending/снимка в IndexedDB `tm-chanel-normalizer-production-v1`; после — подтверждённый snapshot и завершение записи журнала. Без слепых PUT/POST retries. Если write был прерван, повторный запуск сначала GET-сверкой доказывает outcome pending и только тогда продолжает. Любая неоднозначность / RU drift / потеря KK Media или `key` / лишние связи => GLOBAL STOP. Ошибки конкретной Category без записи допускают skip и фиксацию в общем CSV/JSON. Между write используются небольшие паузы, не запускать тысячи параллельных запросов. Финальные JSON/CSV скачиваются автоматически.

## Риск и продолжение

Независимой резервной копии Strapi DB нет. JSON/IndexedDB evidence не является серверным backup и не гарантирует восстановление. Запуск JS **сразу разрешает production-действия** при наличии необходимых изменений (прямое решение пользователя 18.11.2026); отдельных apply-флагов/подтверждений нет. Запускать в открытой вкладке Admin, не обновлять её посреди работы. Для управляемой остановки между операциями: `window.tmChanelStop=true`. После остановки повторный запуск того же JS продолжит уже проверенный результат, а неоднозначные pending-записи без доказательства исхода заблокирует. Финальные `chanel-normalization-production-YYYY-MM-DD.json` и `chanel-normalization-production-results.csv` содержат counters, по-category statuses и incomplete/errors.
