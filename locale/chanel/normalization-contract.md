# CHANEL — контракт нормализации категорий RU → KK

> Статус: согласованные правила и результаты **read-only** проверки от 18.11.2026. Это не разрешение на массовые записи. Реальная реализация PUT/POST для CHANEL ещё не проверена.

## Scope и источник

- Только бренд CHANEL: `api::brand.brand / yeag7mng9hfpk7pd4ggm7495`, RU relation `categories`; первичный список `chanel-categories-ru.json` содержит 65 уникальных Category `documentId`.
- RU **Draft** — источник семантических значений; реальный список записей и данные перечитывать непосредственно перед каждым изменением, не считать экспорт актуальным live state.
- Для каждой Category учитывать RU/KK Draft и Published, включая **все** root relations и доступные nested relations. Снимок RU/KK до изменения, postflight проверка после каждого PUT/POST, экспорт файлов. Статус `modified` сам по себе не означает несогласованное изменение.
- Создание KK, обновление полей и публикация — отдельный write-этап, после защитного пилота. Снимок в JSON не заменяет независимую резервную копию БД при риске повреждения Strapi i18n.

## Уточнённое пользователем правило Media — 18.11.2026

**Любое уже заполненное Media в KK сохранять**, даже если его numeric ID или сам файл отличается от RU. Это действует на все Media schema-типа — корневые, внутри обычных и повторяемых компонентов и на любой глубине Dynamic Zone, включая `dynamic[].items[].image`, `brandZoneBanners[].image` и другие вложенные поля. Не зависеть от `pluginOptions.i18n.localized`: содержимое KK защищено независимо от флага, пока реальные postflight-проверки не подтвердят отсутствие кросс-локальных побочных эффектов.

- При ненулевом Media в KK сохранить **точный KK asset**; сравнивать по ID/составу, но не переносить русское Media в KK просто из-за отличия объектов.
- Если соответствующее Media в KK пусто — копировать существующее RU Media. Если и RU пусто — без изменения.
- При **новой** KK-локали, где своих Media нет, первоначально используются RU Media в доступных компонентах, если позволяет схема и подтверждённый save contract.
- Различия numeric `id` самих экземпляров компонентов RU/KK не являются бизнес-расхождениями и не повод пересоздавать компоненты.
- Повторяемые компоненты сопоставлять по устойчивым полям (`key`, `__component` и др., если реально уникальны), а не по индексу или numeric ID. При неоднозначности соответствия **пропуск/ручной review**, а не замена всего KK блока.
- Оставшиеся согласованные семантические поля и связи компонента синхронизировать RU → KK, но без уничтожения защищённых KK Media. В том числе нельзя слепо отправлять целиком RU `dynamic` поверх KK.

## Прочие правила нормализации

- `name`: сохранить существующий непустой KK перевод; если KK пусто — заполнить из RU. `title`, Boolean (`active`, `custom`, `showProducts`) и остальные ранее согласованные не-медиа поля нормализовать от RU, с проверкой настоящей schema и ограничений уникальности.
- `productsLabelFilter`, `brandZoneBanners`, `filters_app`, `dynamic`: зеркалировать согласованные значения и порядок с глубокой защитой Media; nested relations проверять по реальным `documentId`, отдельно разрешая KK targets.
- Root relations `parent`, `categories`, `product`, `brand`, `top_brands`: RU состав → соответствующие KK targets; отсутствующий KK target записывать как pending link и продолжать независимые поля. Не создавать и не менять чужие Product/Brand автоматически. Перед созданием parent/children links может потребоваться сначала создать все 64 отсутствующие KK Category.
- Устаревшая `products` должна быть пустой RU/KK; непустая RU — явный stop/review для записи, лишние KK links удаляются только по согласованному правилу.
- `key` — **nonlocalized unique shared**: известен live-инцидент с обнулением RU Draft.key при KK PUT. Не отправлять `key` в CHANEL payload без отдельно подтверждённого безопасного контракта и защиты RU; отличия сохранять в pending/review. Уникальный `bitrix_id` также требует предварительной проверки, не угадывать допустимость дублей при создании KK.
- Перед каждым write сохранять полные snapshots четырёх версий/relations, затем проверять семантику RU Draft/Published неизменной. При RU drift, неопределённом ответе PUT/POST, повреждении ключа — GLOBAL STOP, сохранить before/after; никакого автоматического повторного PUT/POST или слепого восстановления.

## Результаты read-only аудита (18.11.2026)

Файл пользователя: `chanel-categories-audit-all.json` (в репозиторий **не загружается**; содержит полные бизнес-данные CMS). Запуск `locale/chanel/categories-audit-all.js` с `complete=true`: 65/65 записей, 1 044 GET, retries=0, errors=0.

- RU Draft: **65/65**, RU Published: **64/65**.
- KK Draft: **1/65** (только `adl0ggt49f808cv4j2xalioq` / `Chanel / Holiday Collection`), KK Published: **0/65**.
- У существующей KK `dynamic[0].items[0].image.id=153056` (KZ-изображение) отличается от RU `153055` (RU-изображение). **Сохранить 153056**. Семантические root relations этого Category совпадают: `product` 10/10 и `brand` 1/1.
- Во всех 65 RU Draft есть 1 `brand-page.banner-slider`. Во всех **64** существующих RU Published `dynamic=[]` и `showProducts=null`, тогда как RU Draft `dynamic` содержит баннер и `showProducts=true`; у **4** дополнительно отличается `filters_app` (Draft заполнено, Published пусто). Поэтому **RU Publish изменит публичный RU-контент**. В исходном запросе было требование Publish обеих локалей, но до write-этапа надо отдельно утвердить необходимость RU Publish: в текущем Category Localizer из-за i18n рисков RU не перепубликуется автоматически.
- Root relation в RU Draft: `product` суммарно 978 связей (321 уникальный Product `documentId`), `brand` 65, `parent` 60, `categories` 60; `products` и `top_brands` пусты. Десять parent Category и все 60 child targets входят в текущие 65; наличие KK у 321 Product **не проверялось**.
- RU `key` заполнен и уникален у всех 65; значения KK `key` остальных 64 пока отсутствуют вместе с локалями. Все 65 RU `title` заполнены. Схема root Media: `largeImage_app`, `preview_picture`, `previewImage_app`, `largeImage`, `detail_picture`, `menu_banner`, `pictures`.

### Безопасный порядок дальнейшей работы

1. Уточнить семантику RU Publish (изменяет все 64 публичные RU категории и часть `filters_app`) перед любым write.
2. Разработать read-only точный план нормализации с учетом создания 64 KK, зависимостей, уникальных полей и глубокого merge Media.
3. Только после проверок/независимого backup БД — single-category write pilot с журналированием и before/after, затем ограниченная партия, и лишь потом массовый запуск.
