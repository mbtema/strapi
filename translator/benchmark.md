# RU → KK Translator Benchmark

## Цель

Сравнить прежнюю архитектуру из трёх отдельных переводчиков (plain text / HTML / image) с текущим единым `ru-kk-translator-prompt.md`.

Важно: это статический архитектурный benchmark. Он оценивает покрытие требований, конфликтность инструкций, безопасность и сопровождаемость. Он не заменяет runtime A/B на реальных переводах.

## Почему новый prompt лучше

### 1. Один source of truth

Глоссарий, защищённые названия, анти-кальки и общие правила больше не дублируются в трёх местах. Это устраняет главный риск старой архитектуры: один термин исправлен в HTML translator, но остался старым в plain/image.

### 2. Явный routing

Новый prompt разделяет:

`IMAGE → EMPTY → HTML → PLAIN_TEXT`.

Специализированные ограничения находятся внутри соответствующих режимов и не должны применяться к остальным типам входа.

### 3. Сильнее API contract

Пустой текст остаётся пустым. Whitespace сохраняется. Вход без переводимого русского текста возвращается без служебного ответа. Plain text и HTML возвращаются без markdown/code fences и дополнительных пояснений.

### 4. Сильнее anti-hallucination

Есть отдельный глобальный запрет придумывать отсутствующие свойства, эффекты, состав, способ применения, условия акции и продолжение неполного текста.

### 5. Сильнее защита идентичности

Защищаются не только бренды, но и торговые названия, технологии, английские оттенки, аббревиатуры и INCI. Запрещено менять написание, регистр, пунктуацию и целостность строки.

## Архитектурные риски нового prompt

### R1. `null` нельзя надёжно решить одним prompt

`""` и whitespace описаны хорошо. Но настоящий API `null` лучше обрабатывать до вызова LLM:

- если source field = `null` → не вызывать переводчик или вернуть `null` по контракту приложения;
- если source field = `""` → можно вернуть `""` без вызова модели;
- whitespace-only также можно short-circuit до модели.

Это дешевле и детерминированнее.

### R2. IMAGE mode зависит от возможностей runtime

Prompt логически описывает image editing, но обычный text-only API не может вернуть готовое изображение только потому, что это написано в prompt.

IMAGE mode использовать только в среде, где реально доступно редактирование/генерация изображений.

### R3. Полный multimodal prompt избыточен для массового text API

Для ручного ChatGPT-проекта полный prompt удобен.

Для массового перевода товаров безопаснее и дешевле иметь один canonical source, из которого API получает профиль:

`CORE + EMPTY + PLAIN_TEXT + HTML`

без IMAGE-блока.

Это не второй независимый prompt и не второй глоссарий: это compiled profile из одного source of truth.

### R4. Определение HTML можно сделать строже

Текущее правило «если вход содержит HTML-разметку» достаточно для обычного `detail_text`, но потенциально двусмысленно для plain text с угловыми скобками или HTML-подобным техническим фрагментом.

При появлении реального сбоя routing стоит уточнить критерий HTML, а не усложнять его заранее.

## Методика runtime-оценки

Для text/HTML тестов:

- 1 балл — PASS;
- 0 баллов — FAIL;
- никакого half-pass для структурных и safety требований.

Отдельно считать:

- Translation accuracy;
- Glossary compliance;
- Protected-token integrity;
- Structural integrity;
- Hallucination rate;
- Output-contract compliance.

Для массового API ключевой показатель:

`critical_fail_rate = (hallucination + wrapper + protected-token corruption + HTML corruption) / total`

Новый prompt можно считать практически лучше старого только если:

1. общий pass rate выше;
2. critical fail rate ниже;
3. на реальной выборке качество казахского не ухудшилось.

## Рекомендация по deployment

### ChatGPT / ручная работа

Использовать полный `ru-kk-translator-prompt.md`.

### Массовый API

Лучший вариант:

1. до LLM short-circuit для `null`, empty и при необходимости whitespace;
2. использовать текстовый профиль из того же canonical prompt: CORE + EMPTY + PLAIN_TEXT + HTML;
3. IMAGE оставить только для image-capable runtime;
4. вести один общий glossary/source of truth.

## Вывод

Новая архитектура объективно лучше старой по покрытию, согласованности и сопровождаемости.

Использовать один multimodal prompt безопасно для ручного translation-проекта, потому что режимы явно разделены и имеют собственные ограничения.

Для массового API полный multimodal prompt допустим, но архитектурно оптимальнее использовать производный text-profile из того же canonical source и не передавать IMAGE-инструкции в каждый товарный запрос.

Главные оставшиеся риски находятся не в переводческих правилах, а на границе runtime: обработка `null`, capability routing для изображений и возможная неоднозначность определения HTML.
